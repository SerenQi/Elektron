# PITFALLS · 踩过的坑

现象 / 根因 / 修法。全是真事故，不是假想。

---

## 记忆

### 开了向量召回，反而找不到东西

**现象**：打开 embedding 之后，一些明明关键词能命中的记忆再也召回不出来。

**根因**：向量结果被拿来**替换**候选集，而不是和关键词结果合并。
向量是后台慢慢补的，补全之前大部分桶都没有向量——它们在这一步整批消失。

**修法**：两路各自召回，取并集进精排；语义相似度和字面分在同一维取较高者。
向量服务慢或挂了，也只影响语义那一路，关键词结果照常返回。

### 中文词嵌在句子中间就搜不到

**现象**：原文层搜一个三字词，明明几十条对话里都有，只返回一小部分。

**根因**：FTS5 默认分词器把一整段连续中文当成一个词，只有碰巧被标点隔开的才命中。

**修法**：另建一张 `tokenize='trigram'` 的索引表（`context_index.py`），写入时两张表同一事务写；
三字及以上走 trigram MATCH，一两个字的词走 LIKE；新表查不到再回退旧表。

### 导入时读到写了一半的行，那条永远丢了

**现象**：偶发地少几条对话，事后怎么重跑导入都补不回来。

**根因**：对方正在追加的最后一行还没写完，解析失败被跳过，但收尾时偏移量已经越过了这半行。

**修法**：偏移只推进到"最后一条完整记录之后"，没有换行结尾的行留给下一轮从头读。

### 一条记忆被召回过一次，就再也召回不出来

**现象**：某条记忆在一段对话里被吸上来过，之后所有对话都吸不到它，重启进程才恢复。

**根因**：去重用的是进程级的 set，永不清理，也不分会话。

**修法**：按会话隔离、半小时过期（`recall_engine.RecallHistory`）；明确想重问时可传 `refresh`。
同类问题：被衰减引擎自动标成 resolved 的旧记忆也被直接跳过——"已经解决"不等于"今天想不起来"，改成降权 0.6。

### 搬家之后，所有旧记忆的排序全乱了

**现象**：把几百条历史记忆批量导入新库，之后召回结果整个歪掉——
新导入的那批永远排在最前面，真正最近的记忆反而沉底。

**根因**：创建接口没有 `last_active` 参数，内部一律写当前时间。
而召回的时间权重取的正是 `last_active`。于是几百条几十天前的记忆，
时间分集体拉满。

**修法**：导入时 `last_active := created`。并且——
**导入接口必须支持显式指定所有时间字段**，这是批量迁移的基本要求。

**教训**：时间戳字段不止一个的时候，先查清楚哪个参与排序。

### 同一批数据导入了两遍

**现象**：导入完发现文件数是预期的两倍，每条记忆各有两份。

**根因**：第一个后台导入进程启动后，看日志只输出了几条就判断它死了，
于是又启动了第二个。实际第一个一直活着，两个并行跑完。

**修法**：清理时按导入映射表移除第二批（移走不删，留退路）。

**教训**：判断进程死活要用 `pgrep`，不要看日志条数——日志有缓冲。

### 用 pgrep 判断进程时把自己也算进去了

**现象**：写了个 `until ! pgrep -f "xxx.py"; do sleep 5; done` 等导入结束，
结果它等了半小时还没退出，而导入早就跑完了。

**根因**：这条 shell 命令的命令行里**包含了被搜索的字符串**，pgrep 每次都能搜到它自己。
它在等自己结束。

**修法**：用 `pgrep -f "xxx" | grep -v $$`，或者干脆检查 PID 文件。

**教训**：任何"检查某进程是否存在"的命令，先确认它不会匹配到自己。
同类问题在 `ps | grep` 里也一样。

### 中文短词被检索阈值挡在外面

**现象**：查询"杯子"没有任何召回，查询"杯子在哪儿"就正常。

**根因**：为了过滤无意义输入，设了"少于 4 个字符直接跳过"。
这个阈值是照着英文定的——英文 4 个字符还组不成一个实词，
**中文两个字已经是一整个词了。**

**修法**：阈值降到 2，只挡单字。

**教训**：任何按字符数做的判断，都要分别验证中英文。

### 自称增量的导入脚本，其实每次都在重读全量

**现象**：原文层看起来是活的，实际停在几小时前。

**根因**：脚本用"已处理行数"记断点，每轮仍要把每个文件从第一行读到断点。
语料涨到几千个 jsonl、几个 GB 之后一轮十几秒，慢到没人愿意挂 cron。

**修法**：状态表加 `mtime` 和 `bytes_done`。mtime 没变的文件整个跳过，
变了的 `seek(bytes_done)` 直接跳到断点。同一份语料 10.5 秒 → 0.216 秒。

**配套坑**：`for line in fh` 迭代之后调 `fh.tell()` 会抛
`OSError: telling position disabled by next() call`。要记字节偏移，
循环得写成 `while True: line = fh.readline()`。

**教训**：判断一个定时任务健不健康，看它实际多久被执行一次，不看它的设计。

### 换了新库之后，旧库还有人在读

**现象**：记忆已迁到新库并持续写入，展示层的条数一直不动。

**根因**：展示层的只读 API 里写死了旧库路径。迁移时改了所有写的地方，漏了读的地方。
旧库作为只读存档没被删，于是一切照常运行，只是永远停在迁移那一刻。

**修法**：换数据源，让展示层直接读新库的存储格式。

**教训**：迁移的验收标准不是"新库写进去了"，是"把旧库改名，看看什么报错"。

## 状态

### 情绪引擎跑了三千多次，事件账本一条都没有

**现象**：驱动力数值一直在动，但事件账本是空的。
表面看系统在运行，实际它与真实对话完全脱钩，在自己内部空转。

**根因**：两层。
① 配置里缺少分类器要找的那个环境变量名（有别的变量装着同一个 key，但名字不对），
导致"分类器是否可用"恒为 false，静默跳过；
② 注释里写明该由某个组件在每轮对话后投递对话窗口——**而那个组件从来没被实现过。**

**修法**：补配置 + 写投递器（定时扫对话流水，取最近 N 轮 POST 给引擎）。

**教训**：
- "可用性检查返回 false 就静默跳过"是最危险的降级方式——它让系统看起来在跑。
  任何 feature flag 为 false 时至少要打一条日志。
- 注释里写"由 X 负责调用"的时候，去确认 X 真的存在。

### 闭环回写每十分钟空转一次

**现象**：回写脚本的日志连续几十次都是 `0 0 0`。

**根因**：它读的记忆库地址，和实际写入记忆的地址不是同一个。
两套记忆系统并存期间，写进了 A，回写脚本去敲 B。

**教训**：系统迁移期间，**先确认读写两端指向同一处**，再谈功能。

## 行为

### 队列里的冲动卡了 129 小时没人执行

**现象**：daemon 正常生成冲动，队列正常写入，日志一直打印 `queue pending: 1`，
但那条冲动五天没被执行。

**根因**：生成和执行之间没有唤醒机制。队列写完就等着 agent"下次醒来自己去看"，
而 agent 醒来的时机完全由别的因素决定。

**修法**：见 DECISIONS「唤醒不是提醒」。

**教训**：**对不会自己醒来的东西，"写进待办"等于什么都没做。**

### 给进程发信号误伤了别的进程

**现象**：按 PID 文件发信号，但 PID 文件可能是陈旧的——
原进程已死，系统把这个 PID 分配给了别的进程。
`os.kill` 只能捕获"进程不存在"，捕获不到"换人了"。

**修法**：发信号前双重校验 `/proc/{pid}/cmdline` 和 `/proc/{pid}/cwd`。
两者都对才发。宁可不发，不能误伤。

**已知代价**：cmdline 校验依赖启动参数的具体写法，改启动方式时要同步改这里。
这是有意选择的保守做法。

## 通用

### 验证脚本查的是一份不生效的副本

**现象**：验收一个改动时，代码明明还在旧逻辑上，报告却说改完了。
查了半天以为对方虚报。

**根因**：查的是宿主机上的源码目录，而**实际运行的是容器镜像里的那份**——
只有两个文件是从宿主机挂载的，其余都在镜像内部。

**教训**：验证"线上是什么样"的时候，先确认你看的那份文件真的在跑。
容器、软链、多副本、缓存——每一样都能让你查错地方。

### 无 User-Agent 的请求被 CDN 拦截

**现象**：验证脚本请求服务返回异常，误判服务挂了。

**根因**：CDN 会拦截没有 User-Agent 头的裸请求。

**修法**：验证脚本一律带 UA。
